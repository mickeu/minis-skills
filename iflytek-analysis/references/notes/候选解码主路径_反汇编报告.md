# 讯飞输入法候选解码主路径反汇编报告

> 样本：iFlytekIME arm64 Mach-O。证据仅来自指定的 14 份现成反汇编，未重新反汇编。  
> 标记：**事实**表示指令直接证明；**推断**表示结构/业务命名尚需动态验证。

## 一、结论先行

1. 主路径确实以 **6 字节 FST 词项**为基本单位。词项布局可确定为 `{u32 packed; u16 id4}`：`packed` 的低 24 位用作 arc/资源索引，高 8 位是属性；`+4` 的 `u16` 在 `ProcessEmitDecode_common` 中同时承担词项匹配键，并经 `ctx+32` 映射到内部 ID。不能仅凭当前切片把前三字节直接命名为“笔画码”。
2. `ProcessEmitDecode_common` 的入口参数可还原为 `x0=解码器/expander, x1=FstEpdParam*, x2=辅助表/上下文`。它从 `param+0` 取展开结果，从 `param+8` 取当前 arc-state/emit 上下文；词项表来自 `param->expandRes+16` 所指对象的虚函数结果，再取返回对象 `+16` 的基址，边界由相邻 offset 表确定。
3. 每个命中词项并不是直接构造 DecodeNode。公共循环先用 `entry+4` 找到内部词 ID，检查有效表，再在每个候选槽的 `vector<DecodeArcState*>` 中寻找 `state->inner(+8)->key(+0)` 等于当前目标指针的状态，经过 flags/type 条件后调用 `process_chn` 或 `process_eng`。
4. `process_chn`/`process_eng` 都是**候选生产/入桶器**，本身不调用本报告给出的 `ConstructDecodeNode@0x1013acf58`。中文路径调用 `0x1013e0668` 产生一个中间候选并 push 到 `ctx+16` vector；英文路径更复杂，会复制/变换 ArcState、枚举英文变体并把对象 push 到多个桶。真正 DecodeNode 组装由后续 `ConstructDecodeNode` 独立完成。
5. `ConstructDecodeNode` 遍历输入 `vector<DecodeArcState*>`，逐个调用 `0x10138d564` 创建 DecodeNode；该被调函数不是本素材中的 `CreateNode@0x10138de40`。随后按 type `0x5b` 做场景过滤；未被过滤者头插入桶链，并递减桶容量/剩余数。`CreateNode` 则明确调用 `SetInfo@0x10138e0b0`，证明 NodeCreator 的公共字段复制布局。
6. `MergeOne`/`MergeN`/`MergeOneForPC` 不是“比较分数后保留较优节点”的普通去重。它们按节点类型、flags 和边界位置决定**链拼接、头尾替换或生成组合节点**；被移出的一侧调用回收函数。`MergeN` 逐项扫描输入向量并调用 `MergeOne`，必要时把组合结果继续并入目标桶。静态证据不足以给所有 bit 命名，不能编造为“总保留高分”。

## 三、上游：从展开弧到词项指针

### 3.1 ProcessEmit

入口保存 `x0→x20, x1→x22, x2→x23, x3→x21`。它首先要求：

```asm
1013e20a0 ldr x8,[x20,#8]
1013e20a4 cbz x8,...
1013e20ac ldr x0,[x22,#16]
1013e20b4 ldr x8,[x22,#24]
1013e20bc ldr x8,[x22,#32]
1013e20c4 ldr x8,[x22,#48]
```

因此 `x1` 对象至少含 `+16/+24/+32/+48` 四个关键资源。`[x2]` 的模式值为 1 或 3 时走专门校验/查表，其他模式调用内部通用分支 `0x1013e278c`。它还把展开对象中取出的指针/索引写到 `x0+32/+40`，随后构造临时参数，交给后级 emit/decode。错误分支主要是日志，正常返回 0。

### 3.2 ProcessArcOut

它经 `param+16` 对象的虚函数取表描述：

```asm
1013e4018 ldr x8,[x0]
1013e401c ldr x8,[x8,#80]
1013e4020 blr x8
1013e4024 ldr x8,[x0,#8]
1013e4028 ldp w12,w9,[x8,#8]
1013e4030 ldp x14,x8,[x8,#16]
```

随后由 `param+48` 的状态得到起始 arc index：若 flags bit15 未置位，则 `(*(u32*)[+24]) & 0xffffff`；否则使用另一默认索引。offset 表元素取 `bits[1..24]`：

```asm
ldr w11,[x14,w10,uxtw #2]
ubfx w23,w11,#1,#24
ldr w10,[x14,(w10+1),uxtw #2]
ubfx w4,w10,#1,#24
```

这得到 `[begin,end)`。若词弧模式成立，调用 `ProcessArcOut_word`；否则按 `tableBase + 6*begin` 顺序把每个词项地址 push 到临时 vector。明确证据：

```asm
1013e43f4 umaddl x28,w23,w10,x11 ; w10=6
1013e4404 add x28,x28,#6
```

### 3.3 ProcessArcOut_word

`x2` 是输出 `vector<entry*>`，`x3/x4` 是 `[begin,end)`，`x5/x6` 是指定词 ID/模式。若没有直接 ID，它先经虚函数取得一组 `u16` ID；然后双重循环比较：

```asm
1013e3f1c ldrh w8,[x28,#4]
1013e3f20 ldrh w9,[idList,x22,lsl #1]
1013e3f24 cmp w8,w9
```

相等即把该 6B 词项指针压入输出 vector。因此 `entry+4` 是词项筛选键/词 ID 这一点为事实。

## 四、ProcessEmitDecode_common 完整控制流

### 4.1 参数和主要寄存器

- `x0→x19`：解码器/expander 实例。
- `x1→x20`：FstEpdParam；`+0` 展开结果，`+8` 当前 emit/ArcState 上下文。
- `x2→x28`：候选槽/辅助表上下文。
- `x21=[x20]`：展开结果对象。
- `x23=[x20+8]`：当前上下文；`+24` 是槽有效位图，`+72` 是 ID 有效表，`+96..+112` 是 `u16` 槽索引 vector。
- `x24=[[x21+48]+8]`：ArcState 搜索时的上界/目标指针。
- `x25`：词项低 24 位 rank/属性表基址。
- `x26`：当前 6B 词项。

### 4.2 词项表来源与区间

```asm
ldr x21,[x20]
ldr x8,[x21,#48]
ldr x24,[x8,#8]
ldr x0,[x21,#16]
... vcall +80 ...
ldr x25,[x0,#16]
ldr x9,[x0,#8]
ldp w13,w9,[x9,#8]
ldr x13,[x9,#16]
```

由同族 `ProcessArcOut` 可知返回对象描述 offset 表和 6B 数据表。`param->expandRes+48` 的 `+24/+32` 提供当前 arc 的 offset 索引与 flags：

```asm
ldr x10,[state,#32]
tbnz w10,#15, special_index
ldr x12,[state,#24]
ldr w12,[x12]
and w14,w12,#0xffffff
ldr w12,[offsets,w14,uxtw #2]
ubfx w13,w12,#1,#24       ; begin
ldr w12,[offsets,(w14+1),uxtw #2]
ubfx w13,w12,#1,#24       ; end
```

循环末端 `add x26,x26,#6`，直到 `x26==endPtr`。

### 4.3 每词项过滤

1. 读取 ID：`ldrh w8,[x26,#4]`。
2. 与 `decoder+40` 的当前词 ID 比较；若相等走收尾/日志分支。
3. 经 `decoder+32` 的 `u16` 映射表把词项 ID 转成内部 ID：`ldrh w8,[map,w8,lsl #1]`。
4. 查 `x23+72` 字节有效表，值 0 则跳过。
5. 查 `x23+24` 的槽位有效 bitmap：`1 << (slot&31)`。
6. 从 `x23+24 + 24*slot` 取得该槽的树/链头，沿 `node+32` 排序键查到覆盖 `x24` 的区间。
7. 读取词项 `packed`：`ldr w9,[x26]; and w9,#0xffffff`；越界则跳过；`ldrsb [x25+index]` 得 rank/类别值并写临时参数。

### 4.4 定位 DecodeArcState 链

槽对象 `x28` 中每项是 vector/桶；取出元素后：

```asm
ldr x8,[bucketArray]
ldr x8,[x8,x22,lsl #3]    ; 候选对象
ldr x9,[x8,#8]             ; DecodeArcState 内部指针
ldr x10,[x9]               ; key/owner
cmp x10,x24
```

必须匹配目标指针。之后还检查：

- `inner+21` 的 `0x6` 位（特定模式下要求清零）；
- 展开类型 `expandRes+4` 是否为 `0x59/0x5b`；
- `inner+16` 的 bit0/bit15；
- 当前目标对象 `+16` 的类型/状态字节。

最终分流：

```asm
ldr x8,[candidate]
ldr x8,[x8,#0]
ldrb w8,[x8,#33]
tbnz w8,#1, call_eng
bl 0x1013e6974             ; process_chn
...
bl 0x1013e6374             ; process_eng
```

故中英文分流依据是候选关联对象 `+33 bit1`，不是根据 Unicode 文本即时判断。

### 4.5 文字 CFG

```text
参数校验
 └─ 取展开结果、offset 表、6B 数据表
     ├─ flags.bit15 ? 特殊 begin : state+24 的低24位 begin
     ├─ 计算 begin/end（offset 元素 bits1..24）
     └─ for entry in [base+6*begin, base+6*end):
          ├─ id16=entry+4 → decoder 映射 → 有效表/bitmap
          ├─ 定位覆盖目标指针的槽树节点
          ├─ packed.low24 → rank/属性表；清输出 rank/状态
          └─ 遍历槽内 DecodeArcState*
               ├─ inner.key != target：继续
               ├─ flags/type 不满足：继续
               ├─ owner+33.bit1=0 → process_chn
               └─ owner+33.bit1=1 → process_eng
```

### 4.6 可移植伪代码

```cpp
int ProcessEmitDecodeCommon(Decoder *d, FstEpdParam *p, Aux *aux) {
    auto *res = p->expandRes;
    auto *ctx = p->ctx;
    if (!ctx) return ERR_NULL;

    TableView tv = res->fstProvider->virtual_get_table();
    Range r = arc_range(tv.offsets, res->arcMeta);
    for (Entry6 *e = tv.entries + r.begin; e < tv.entries + r.end; ++e) {
        uint16_t rawId = e->id4;
        if (rawId == d->currentWordId) continue;
        uint16_t innerId = d->idMap[rawId];
        if (!ctx->validId[innerId]) continue;

        unsigned slot = resolve_slot(ctx, innerId);
        if (!(ctx->slotBitmap & (1u << (slot & 31)))) continue;
        auto *rangeNode = find_covering_node(ctx->slotTree[slot], ctx->target);
        if (!rangeNode) continue;

        int8_t rank = tv.rankByIndex[e->packed & 0xffffff];
        for (DecodeArcState *s : aux->buckets[slot]) {
            if (s->inner->key != ctx->target) continue;
            if (!flags_accept(res, s, rangeNode)) continue;
            EmitArg a{e, s, rank, /* flags/type/range */};
            if (s->owner->flags33 & 2) process_eng(d,p,&a,&status);
            else                       process_chn(d,p,&a,&status);
        }
    }
    return 0;
}
```

`Entry6.packed` 内部三个字节的进一步子字段，本函数没有逐字节读取，故待验证。

## 五、process_chn 与 process_eng

### 5.1 process_chn (`0x1013e6974`)

输入中 `x2` 是公共循环构造的临时 EmitArg，`x3` 是输出状态指针。它先取 `arg+16`、其中 `+8` 的 ArcState，再根据 ArcState 是否存在及 `+16` 字节生成小标志；随后把 `*status=0`。

主生产调用：

```asm
ldr x0,[decoder,#16]
ldrb w3,[meta,#4]
ldr x6,[arg,#8]
ldrb w4,[x6,#3]
ldrh w5,[x6,#4]
ldr x7,[container]
str x8,[sp]
bl 0x1013e0668
```

`0x1013e0668` 返回候选对象，随后直接 push 到 `[param+16]` 的 vector：

```asm
ldr x0,[x19,#16]
ldp x9,x10,[x0]
str x8,[x9]
add x8,x9,#8
str x8,[x0,#8]
```

如果上下文 `+152` 非零，还执行 type/id/长度门控，并维护 `ctx+120/+124/+128/+132` 四个阈值以及产物 `+44/+48` 状态。末尾把 `(node+44 != 0 && node+48 == 0)` 写回状态。

**分工结论**：中文路径调用专门工厂 `0x1013e0668` 生成中间候选并入 emit vector；不直接调用 `ConstructDecodeNode`。

### 5.2 process_eng (`0x1013e6374`)

英文函数 384 行、分支显著更多。可确认行为：

- 从 EmitArg/ArcState 拷贝字段到栈上临时结构；
- 根据 flags/type (`0x59/0x5b` 等) 选择不同英文状态变换；
- 多次调用 `0x1013dfe1c` 一类工厂/克隆函数；
- 遍历英文变体/segment vector，并把返回对象 push 到输出 vector；
- 处理 `+44/+48/+120/+124/+128/+132/+152` 限额与门控，和中文路径共享输出约定。

它同样**没有** `bl 0x1013acf58`，因此不直接构造最终 DecodeNode。英文候选的具体大小写、补全、纠错 bit 含义在当前无符号切片中不能唯一命名，待验证。

### 5.3 缓存路径

`ProcessEmitDecode_cache` 重用已缓存的槽索引 vector（`ctx+96..112`），仍以 6B 范围扫描、按 `entry+4` 匹配，并在 `0x1013e5d80/0x1013e5d98` 分别调用 chn/eng。它是索引/ArcState 查找的快速路径，不是另一套候选格式。

## 六、ConstructDecodeNode 与 NodeCreator

### 6.1 ConstructDecodeNode (`0x1013acf58`)

它遍历 `x2` 指向的 `vector<DecodeArcState*>`。每项调用：

```asm
ldr x1,[input,index,lsl #3]  ; ArcState*
ldr x2,[x22,#8]
ldp x3,x4,[x22,#32]
mov x0,x21
bl 0x10138d564
```

返回 `DecodeNode*`。这里的 `x21` 是 NodeCreator/allocator，`x22` 是组装参数，向工厂传入 ArcState、上下文和两个边界/评分值。返回后：

- 若 `node+40 == 0x5b`，调用场景过滤 `0x1013909b4`；过滤状态非零则不入桶。
- 否则头插入 `bucket=[x22+32]` 所指链表：`node->next=*head; *head=node`。
- `bucket+72` 递减 1，表明它是剩余额度/待处理计数，而非候选总数。

`ConstructDecodeNodeInScene` 基本相同，遍历 vector、调用 `0x10138d564`、type 0x5b 时做场景过滤、成功者头插桶。不同点主要是上下文取值和输入 vector 的所有权（结束时会销毁/清理临时 vector）。

### 6.2 CreateNode (`0x10138de40`) 与 SetInfo

`CreateNode` 是另一个明确的 NodeCreator 路径：先从池取节点，然后调用 `SetInfo@0x10138e0b0`。因此不能把 `ConstructDecodeNode` 的直接 callee `0x10138d564` 错写成当前 `CreateNode`；它们属于同一 NodeCreator 家族但地址不同。

`SetInfo(x0=creator, x1=prevNode, x2=ArcState/info, x3=DecodeNode)` 的字段复制：

| DecodeNode 偏移 | 来源/语义 |
|---:|---|
| `+0` | `src+8` 指针 |
| `+8` | `src+16` 指针 |
| `+16` | 前驱 DecodeNode 指针 `x1` |
| `+24` | `src+24` 指针 |
| `+32` | `src+0` 的 `u16`，某些 type 范围额外 OR `0x200000`；这是 packed flags/id 字段 |
| `+40` | `src+3`，候选 type；已见 `0x5b` 特判 |
| `+41..42` | 清零 |
| `+43` | 继承前驱 `prev+43` |
| `+44` | 保留原值高两位 `0xc0000000`，其余清零；后续路径写状态/flags |
| `+48` | `src+6` 的 `u16`；可视为词项 ID/内部 ID 字段，正式名待验证 |
| `+50` | 前驱 `+50` 加源链首字节长度 |
| `+51` | 前驱 `+51`，并按 `src+6`/源链长度累加 |

关键指令：

```asm
10138e0c8 ldrh w8,[x2]
10138e0cc str x8,[x3,#32]
10138e0e8 strb w9,[x3,#40]
10138e0f4 ldr w8,[x3,#44]
10138e0f8 and w8,w8,#0xc0000000
10138e10c ldrh w8,[x2,#6]
10138e110 strh w8,[x3,#48]
```

### 6.3 关于 rank

公共循环的 `int8 rank` 被放入 EmitArg，中文/英文生产工厂消费它；`SetInfo` 没有单独的 `rank` 写指令。由此可确定 rank 已在中间 ArcState/info 或传给 `0x10138d564` 的评分参数中折叠。仅凭这 14 个函数无法唯一指出 DecodeNode 的独立 rank 偏移，必须标为待验证。

## 七、MergeOne / MergeN / MergeOneForPC

### 7.1 通用语义

三个函数操作的是链式 DecodeNode/桶，而不是简单数组排序。参与判定的稳定字段包括 `node+32` packed 标志、`+40` type、`+44` flags/status、`+48` id，以及 `node+0/+8/+16/+24` 的链/资源指针。合并结果存在三类：

1. 原节点可直接拼链：更新 next/head/tail；
2. 两节点满足组合条件：调用 NodeCreator 创建组合节点；
3. 冲突或被替代节点：调用缓存管理器回收。

### 7.2 MergeOne (`0x1013adec4`, `0x260`)

控制流是：空桶直接插入；非空时比较候选 type/flags 和边界关系；兼容则拼接或生成组合节点；不兼容则保留原链并回收传入节点。它没有读取一个统一 float/double score 后做 `max/min`，所以不能描述为“分高者胜”。最终保留哪一节点由结构兼容和候选类别决定。

可移植抽象：

```cpp
DecodeNode *MergeOne(MergeCtx *m, DecodeNode *head, DecodeNode *n) {
    if (!n) return head;
    if (!head) return n;
    if (!compatible(head,n)) { recycle(n); return head; }
    if (can_link(head,n)) return splice(head,n);
    DecodeNode *c = create_combined(m,head,n);
    recycle_consumed(head,n,c);
    return c;
}
```

### 7.3 MergeN (`0x1013ad5a4`, `0x57c`)

遍历一个 `DecodeNode*` vector/链集合，对每项执行类型过滤、边界检查，再调用单项合并逻辑；组合产物会继续进入目标桶。它是批量 fold：

```cpp
for (DecodeNode *n : inputs)
    dst = MergeOne(ctx,dst,n);
```

实际还有 scene/type `0x5b` 及 flags 的分支，不应省略为单纯去重。

### 7.4 MergeOneForPC (`0x1013adb20`, `0x3a4`)

这是 PC/特殊上下文版本，额外检查上下文指针和候选边界，合并允许条件比 MergeOne 更严格；满足条件时同样可能调用 NodeCreator 产生新节点，而非只在两个输入中二选一。`PC` 的正式业务全称当前无符号证据不足，待验证。

### 7.5 去重与保留规则的边界

**已确认**：同一链/桶内只有结构兼容者才合并；类型、flags、边界不一致会拒绝组合；被消费节点由池回收。  
**未确认**：是否存在字符串级完全相等比较、哪个 bit 表示“完整句/联想/英文”、组合节点最终 score 的公式。当前材料不允许断言“同词 ID 即去重”或“保留 rank 更高者”。

## 九、对 Rime/笔画输入法的移植要点

1. **资源层保持 6B 紧凑布局但不要强耦合**：建议解析成 `{uint32 packed; uint16 word_id}`，另建 `idMap`、有效位图和 offset 索引；不要在业务层直接指针步进。
2. **分离三层对象**：`LexiconEntry`（只读词项）→ `ArcState`（路径状态）→ `CandidateNode`（输出候选）。讯飞主路径的性能和可维护性正来自不在 FST 命中时立刻构造完整候选。
3. **候选桶索引化**：以 syllable/segment/输入位置为 slot，配 bitmap 快速排除无效槽；Rime translator 可按 segment 起止和 schema/type 分桶。
4. **中英文生产器分开**：中文生产器处理词 ID、场景门控；英文生产器处理变体、补全和大小写。二者共享 EmitArg 和输出桶接口，避免把英文特殊规则塞进通用循环。
5. **使用对象池**：ArcState 固定 40B、DecodeNode 固定布局，适合 slab/free-list；移动端能显著减少候选展开时 malloc 抖动。
6. **合并不要只按文本去重**：键至少应含文本/词 ID、segment 边界、候选类型、语言和完整/联想状态。组合候选应新建不可变节点，统一回收被消费对象。
7. **rank 传递显式化**：讯飞通过临时 EmitArg/工厂参数隐式折叠；移植时建议定义 `CandidateScore {lexical, path, user_freq, penalty}`，避免字段语义丢失。
8. **安全性**：所有低 24 位索引、ID 映射、offset 区间必须先做边界检查；6B 非自然对齐结构应使用 memcpy/显式 little-endian 读取，避免未对齐 UB。
