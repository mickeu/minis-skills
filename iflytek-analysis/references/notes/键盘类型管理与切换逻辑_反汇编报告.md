# 键盘类型管理与切换逻辑：反汇编报告

> 目标版本：讯飞输入法 v15.0.3606（iOS/arm64）  
> 范围：ObjC 键盘类型决策、全局切换、布局文件解析、布局/高度适配。  
> 证据约定：地址均为 Mach-O VA。由于现有 `dis.py` 抽取后 `objdump -b binary` 将切片重定位为 `0x100000000`，本文地址已按“函数 VA + 切片内偏移”回算。

## 一、结论先行

1. `KeyboardTypeManager +getNewKBType:isSecurity:pluginServiceContainer:userConfig:keyboardConfig:`（`0x1001d0b08`）不是“遍历所有键盘”的管理器，而是**按系统输入场景枚举（参数1，0…8）映射内部键盘类型**的纯决策器；默认返回 11。确定映射结果仅出现 `{11,12,13,14,20}` 以及来自 `keyboardConfig` 的两个动态整数值。
2. ObjC ABI 参数为：`x0=类，x1=_cmd，x2=场景/输入类型，w3=isSecurity，x4=pluginServiceContainer，x5=userConfig，x6=keyboardConfig`。任务描述中的四个对象参数顺序应据此理解；`x2` 不是 bool，而是 0…8 的场景枚举。
3. 9 项跳表字节为 `[224,39,0,169,233,35,0,145,9]`（文件 VA `0x101119e90`），目标分别落到：
   - 输入 0、2、6 → 动态值 A（函数入口第一次 `keyboardConfig` getter 的结果；输入 2/6 在 `isSecurity!=0` 时强制 12）；
   - 输入 1、5 → 13；输入 3 → 20；输入 4 → 14；输入 7 → 动态值 B（第二次 getter）；输入 8 → 11。
4. `pluginServiceContainer` 只在后半段“特定宿主/插件能力”四级谓词全部成立时参与覆盖：若 `userConfig` 的布尔 getter 为 1，强制 11，否则改用动态值 B。四级谓词的选择器名在本切片中无法可靠恢复，标为待验证，但其短路逻辑和覆盖结果是确定事实。
5. `KeyboardConfig +shareInstance`（`0x100089060`）采用 ObjC/Swift 桥接单例辅助函数，返回保留后的共享对象；`+resolveInstanceMethod:`（`0x10008ae74`）把 `{Class,self}` 与一个固定 selector 交给动态解析辅助函数。该函数本身没有 selector 比较，实际方法表生成在辅助函数 `0x1011ed4e0`。
6. `GlobalKeyManager` 是弱引用转发器/选择面板协调器。`onNextKeyboard` 向数据源发送“选择下一键盘”，`onSwitchToKeyboard:` 对特殊类型 5 走差异化处理，再向 delegate 发送“全局切换”；`onKeyboardRebuild` 则转发重建。`inputView` 通过 `objc_loadWeakRetained` 读取 `self+0x28` 的弱引用，而不是新建视图。
7. `FileParser -parseKeyboardFromPath:completion:`（`0x1002976a4`）本身是**抽象/默认空实现**：completion 非空即同步调用 `completion(nil)`。真正 INI 读取在 `IniFileParser`（`0x10020d168`）：复制 path/block，执行解析入口，并将异步/完成 block 传给工作对象；回调 block 从捕获偏移 `+0x20` 取 completion 并调用。
8. `KBHeightAdjustMgr -setInputView:`（`0x1000ff45c`）和 `BaseLayoutAdjustManager -setBaseView:`（`0x10013f114`）只是属性 setter thunk，分别跳入 Kotlin/Native 生成的属性写入函数，不包含高度公式。真实几何计算在各自后续方法：高度变更函数对原高度做 `base + delta`，依设备类别选择整数/浮点 frame API；布局调整函数遍历 `KBStruct` 的行/键，缩放 frame、修正首末键边缘，并在左右模式（mode==2）镜像横向偏移。

## 二、键盘类型决策核心

### 2.1 参数与所有权

`0x1001d0b08` 开头：

```asm
mov x21,x6        ; keyboardConfig
mov x20,x5        ; userConfig
mov x0,x4
mov x23,x3        ; isSecurity
mov x24,x2        ; 输入场景枚举
bl  0x1010a787c  ; retain pluginServiceContainer
...
```

函数依次 retain `x4/x5/x6`，退出逆序 release，说明后三者均为 ObjC 对象。`cmp x24,#8; b.hi default` 明确 `x2` 为 0…8 的枚举/整数。

### 2.2 精确跳表

函数先取动态值 A，预置 `result=11`，再按 `x2` 跳转：

| x2 场景值 | 跳表目标 | 初始结果 | `isSecurity` 影响 | 语义标注 |
|---:|---:|---:|---|---|
| 0 | `+0x78` | dynamicA | 无 | 系统键盘场景名待验证 |
| 1 | `+0xa4` | 13 | 无 | 待验证 |
| 2 | `+0x78` | dynamicA | security→12 | 待验证 |
| 3 | `+0x70` | 20 | 无 | 待验证 |
| 4 | `+0x8c` | 14 | 无 | 待验证 |
| 5 | `+0xa4` | 13 | 无 | 待验证 |
| 6 | `+0x78` | dynamicA | security→12 | 待验证 |
| 7 | `+0x94` | dynamicB | 无 | 待验证 |
| 8 | `+0x58` | 11 | 无 | 待验证 |
| >8 | `+0x94` | dynamicB | 无 | 越界回退 |

关键指令：

```asm
0x1001d0b54 mov w22,#11
0x1001d0b68 add x9,x9,x10,lsl#2 ; byte-offset jump table
0x1001d0b80 cmp w23,#0
0x1001d0b84 csel x22,x9,x8,ne  ; security ? 12 : dynamicA
```

**重要限制**：现有二进制符号没有内部枚举常量名，因此不能把 11/12/13/14/20无证据地硬标成“拼音/笔画/英文/数字/手写”。可确认的是 UI 资源中同时存在 `qwerty_26cnkey.ini`、`qwerty_26enkey.ini`、`qwerty_bihuakey.ini` 等布局族；枚举号到名称仍需运行时记录或调用 `KeyboardLayoutManager getDisplayNameWithKeyboardType:` 验证。

### 2.3 插件/宿主覆盖

`0x1001d0bb4` 起对 pluginServiceContainer 取对象，并执行四个短路条件：对象等值/身份判断、两个布尔能力检查、一次带固定 selector/常量的查询。仅四者全真才读取 `userConfig`：

```c
if (pluginPredicate1(plugin) && pluginPredicate2(plugin) &&
    pluginPredicate3(plugin) && pluginPredicate4(plugin)) {
    result = userFlag(userConfig) ? 11 : dynamicB(keyboardConfig);
}
```

依据：`0x1001d0bd4/0xe0/0xf4/0x100` 四个 `cbz` 均跳至统一尾部；`0x1001d0c10 cmp w0,#1`，等于 1 设置 11，否则重新调用 dynamicB getter。该覆盖发生在跳表之后，优先级最高。

### 2.4 可移植伪 C

```c
typedef int64_t KBType;
KBType GetNewKBType(uint64_t scene, bool security,
                    id plugin, id user, KeyboardConfig *cfg) {
    KBType dynamicA = CFG_DYNAMIC_A(cfg);   // selector 待恢复
    KBType dynamicB;
    KBType r = 11;
    switch (scene) {
      case 0: case 2: case 6: r = security ? 12 : dynamicA; break;
      case 1: case 5:         r = 13; break;
      case 3:                 r = 20; break;
      case 4:                 r = 14; break;
      case 8:                 r = 11; break;
      case 7: default:        r = CFG_DYNAMIC_B(cfg); break;
    }
    if (PluginP1(plugin) && PluginP2(plugin) &&
        PluginP3(plugin) && PluginP4(plugin))
        r = USER_FLAG(user) ? 11 : CFG_DYNAMIC_B(cfg);
    return r;
}
```

## 三、KeyboardConfig

### 3.1 `+shareInstance`（`0x100089060`）

调用链为“取元类/类型元数据 → 单例辅助入口 → retainAutoreleasedReturnValue → 释放临时对象 → autoreleaseReturnValue”。可移植语义：

```objc
+ (instancetype)shareInstance {
    id token = ResolveClassMetadata(KeyboardConfig.class);
    id obj = RetainAutoreleasedReturnValue(GetSharedInstance(token));
    Release(token);
    return AutoreleaseReturnValue(obj);
}
```

未见 `dispatch_once` 指令不等于非单例；once/静态缓存被封装在被调辅助函数中。

### 3.2 配置状态表

符号表直接证明 `KeyboardConfig` 暴露以下状态：

| 状态 | 类型/用途 |
|---|---|
| `defaultMainKeyboardType` | 主键盘默认类型，带 `correctDefaultMainKeyboardType:` 修正 |
| `normalKBHeightChange` | 普通键盘高度增量 |
| `singleKBHeightChange` / `singleKBWidthChange` | 单手键盘尺寸增量 |
| `singleHandSetting`, `isSingleHandMode` | 单手方向/启用状态 |
| `py9keyDoubleMode` | 拼音九键双布局模式 |
| `strokeKeyDoubleMode` | 笔画键双布局模式 |
| `isHandWritingOn` | 手写入口/模式开关 |
| `isSmallWordInputOn` | 小字/小词输入开关 |
| `isSimpleTransFlag` | 简繁转换标记 |
| `isNightShift` | 夜间模式 |
| `isMicHidden`, `hideBall` | 麦克风/悬浮球显示策略 |
| `isClipboardEnable` | 剪贴板能力 |
| `musicSkinSetting`, `notMusicSkinSetting`, `oldSkin` | 皮肤兼容配置 |
| `deviceDetection` | 设备检测对象 |

`initWithDeviceDetection:`（`0x1000890ac`）调用基类初始化，保存 deviceDetection，并创建 4 个固定观察键组成数组，注册配置观察/通知；这说明高度、单手、布局版本等状态可热更新，不只在启动读取。

### 3.3 `+resolveInstanceMethod:`（`0x10008ae74`）

```asm
ldr x8, fixedClassOrResolver
stp x0,x8,[sp]          ; {KeyboardConfig class, resolver}
ldr x1, fixed selector
mov x0,sp
bl  0x1011ed4e0
```

事实：该函数委托一个固定 resolver 动态补实例方法，没有逐 selector 分支。推断（依据大量成对 getter/setter 且函数尾部为直接 ivar load）：用于配置键的通用动态属性访问。**具体 selector 和 IMP 编码待通过解码 ObjC selref `0x1019026c8`、resolver 数据 `0x10190b9e0` 验证。**

## 四、GlobalKeyManager 全局切换链

### 4.1 对象布局

符号表及 accessor 指令共同确定：

```c
struct GlobalKeyManager {
    NSObject base;
    bool flag_at_08;       // 子对象逻辑中使用
    id object_at_10;
    id KBSelectView;       // ivar符号
    __weak id dataSource;  // _dataSource
    __weak UIView *inputView; // self+0x28：accessor直接 loadWeak
    __weak id delegate;
    __weak id viewLevelController;
    __weak id voiceOpCodeAnalysisProxy;
};
```

### 4.2 `-onNextKeyboard`（`0x1002643fc`）

步骤：获取 `dataSource` 弱引用并 retain；以参数 `1` 调用其“全局选择下一键盘”方法；释放数据源。结合符号表中实现：

- `iFlyKeyboardController -onGlobalSelectNextKeyboard:`（`0x1002582c0`）
- `iFlyKeyboardContainer -onGlobalSelectNextKeyboard:`（`0x1000f6c3c`）
- `iFlyKeyboardContainer -changeCurrentKeyboardToNext`（`0x1000f6ec4`）

容器最终取得当前模式，选择下一个可用模式；候选序列为空/到尾时重新取列表，实现环回。若扫描发现目标具有禁用谓词则继续；找不到有效项时用 fallback 模式并以 reason=1 切换。

### 4.3 `-onSwitchToKeyboard:`（`0x100264430`）

参数类型保存在 `x19`。流程：

1. 取 `dataSource` 与一个当前状态值；
2. 若状态值等于 5，走特殊分支：先向另一服务发送目标类型，再调用 `self` 的埋点/上下文方法并发布一次通知（调用中 `w4=1`）；
3. 否则直接向普通数据源发送目标类型；
4. 两分支汇合后取 `delegate`，调用 `onGlobalSwitchToKeyboard:type`；
5. 正常释放弱引用对象。

伪代码：

```objc
- (void)onSwitchToKeyboard:(NSInteger)t {
    id ds = self.dataSource;
    NSInteger s = CurrentGlobalState();
    if (s == 5) {
        [SpecialKeyboardService() onGlobalSwitchToKeyboard:t];
        [self recordOrCloseSelector];
        PostTypedNotification(/*payload block*/, YES);
    } else {
        [ds onGlobalSwitchToKeyboard:t];
    }
    [self.delegate onGlobalSwitchToKeyboard:t];
}
```

特殊状态 5 的产品名尚未由 selector/字符串证实，不强行命名为手写或符号。

### 4.4 `-onKeyboardRebuild`（`0x1002642e4`）

该地址处仅一条尾调用，转发到 `0x1010363fc`。紧邻后续桥接函数则是取对象、调用 rebuild 协议再释放。结论：GlobalKeyManager 不亲自构造键盘，它只触发下游 controller/container 重建。

### 4.5 `-inputView`（`0x1002645cc`）

```asm
add x0,x0,#0x28
bl  objc_loadWeakRetained
b   objc_autoreleaseReturnValue
```

等价于：

```objc
- (UIView *)inputView { return self->_inputView; } // weak, loadWeakRetained
```

因此切换期间视图生命周期由 controller/container 持有，GlobalKeyManager 不拥有视图。

## 五、布局文件加载

### 5.1 抽象层 `FileParser`

`-[FileParser parseKeyboardFromPath:completion:]`（`0x1002976a4`）完整实现只有：

```asm
cbz x3,ret
ldr x2,[x3,#16]  ; block invoke pointer
mov x0,x3
mov x1,#0        ; nil result
br x2
```

即：

```objc
- (void)parseKeyboardFromPath:(NSString *)path completion:(void (^)(id))done {
    if (done) done(nil);
}
```

这是 Null Object/基类兜底，不读取文件，也不是异步。

### 5.2 实际层 `IniFileParser`

`-[IniFileParser parseKeyboardFromPath:completion:]`（`0x10020d168`）：

1. retain/copy completion；retain path；
2. 调用自身/解析服务，以 path 取得中间对象；
3. 创建解析工作对象；
4. 在栈上构造捕获 completion 的 ObjC block；
5. 调用工作对象的解析方法 `(path, block)`；
6. 释放 path、工作对象和 block。

其 block invoke（`0x10020d238`）为：

```asm
ldr x0,[block,#0x20]   ; captured completion
ldr x2,[x0,#0x10]      ; invoke
br  x2                 ; 转发解析结果
```

因此“异步性”由实际工作对象决定：API 是 completion 风格，调用者不能假设同步；基类兜底同步返回 nil，INI 子类则把 completion 捕获到 block 并交给解析器。

### 5.3 从 INI 到视图

可确认链条：

```text
keyboardType
  → iFlyUIInputViewController getKeyboardStructWithKeyboardType:
  → 选择资源路径（qwerty_26cnkey.ini / qwerty_26enkey.ini /
                    qwerty_bihuakey.ini / skin/panel INI...）
  → IniFileParser parseKeyboardFromPath:completion:
  → 字典/段/键属性
  → KeyStructGenerator / CandKeyStructGenerator structWithDic:
  → KBStruct + 行/键结构
  → BaseLayoutAdjustManager adjustWithKBStruct:
  → iFlyInputManager reloadKeyboard:...keyboardType:...
  → XFKeyBoard / key views
```

证据是符号集中存在 `getKeyboardStructWithKeyboardType:`（`0x10015bb98`）、`reloadKeyboard:...keyboardType:...`（`0x1001b87c0`）、结构生成器和 INI 解析器；资源清单直接包含上述 `.ini`。解析器只生产结构数据，UIKit 视图由 input manager/reload 阶段构建。

## 六、高度与布局适配

### 6.1 两个 setter 不是计算入口

- `KBHeightAdjustMgr -setInputView:`（`0x1000ff45c`）：`x1=x2`，载入属性元数据 `0x101979e60`，尾调 `0x101178fc4`。
- `BaseLayoutAdjustManager -setBaseView:`（`0x10013f114`）：同样载入属性元数据 `0x101939ec0`，尾调 `0x10113930c`。

这两个函数仅把 ObjC setter 桥接到 Kotlin/Native 属性存储（retain/release、write barrier）。所以不能从 setter 本身声称“读取 safeArea/candidate bar”。

### 6.2 `KBHeightAdjustMgr` 的真实高度变更

邻近 `0x1000ff5e8` 的高度变化函数将传入 `double delta` 存于 `d8`，取 inputView 后按设备能力/类别分支：

```c
void ChangeHeight(KBHeightAdjustMgr *m, double delta) {
    View *v = m.inputView;
    if (DevicePredicate()) {
        if (DeviceClass() != 1)
            SetHeightFloat(v, GetHeightFloat(v) + delta);
        // class==1 落入另一公共分支
    }
    if (DeviceClass() == 1)
        SetHeightInteger(v, (int64_t)CurrentIntegerHeight() + delta);
    else
        SetHeightFloat2(v, DeviceBaseHeight() + delta);
}
```

确定事实：公式是加法 `newHeight = baseHeight + configuredDelta`（`fadd d0,d0,d8` 出现三次）；设备类别 1 用 `fcvtzs` 后的整数 API，其他设备走浮点 API。`KeyboardConfig.normalKBHeightChange/singleKBHeightChange` 是 delta 的配置来源。安全区是否已经包含在 `DeviceBaseHeight()` 中待动态验证，当前函数没有直接 `safeAreaInsets` selector。

### 6.3 `BaseLayoutAdjustManager -adjustWithKBStruct:`（`0x10013f124`）

该函数是真正布局适配入口，核心行为：

1. 取 baseView 的 bounds/frame 和 KBStruct 原始设计尺寸，算横纵缩放比例；
2. 遍历 KBStruct 中的行与键数组；
3. 对每个键 frame 的 x/y/w/h 做比例换算；
4. 首键/末键贴边，消除缩放取整造成的边缘缝隙；
5. 根据模式字段处理左右布局：汇编多处 `cmp wMode,#2` + `fcsel/fneg`，mode 2 时将横向偏移取反，形成右/左单手镜像；
6. 写回转换后的 frame，再交给视图生成。

可移植几何伪码：

```c
void AdjustKBStruct(KBStruct *kb, CGRect dst, int handMode) {
    double sx = dst.w / kb->designWidth;
    double sy = dst.h / kb->designHeight;
    for (Row *row : kb->rows) {
        for (size_t i=0; i<row->count; ++i) {
            Key *k = row->keys[i];
            CGRect r = k->designFrame;
            r.x = dst.x + r.x * sx;
            r.y = dst.y + r.y * sy;
            r.w *= sx; r.h *= sy;
            if (i == 0) r.x = dst.x;
            if (i + 1 == row->count)
                r.w = CGRectGetMaxX(dst) - r.x;
            double side = SideInsetForMode(handMode);
            r.x += (handMode == 2 ? -side : side);
            k->frame = PixelAlign(r);
        }
    }
}
```

候选栏高度更合理的职责位置是上层 `inputHeightManager`（其对象被显式传给 `iFlyInputManager reloadKeyboard:inputHeightManager:...`），再把剩余主键区 bounds 交给 `BaseLayoutAdjustManager`。当前两个 setter 不能证明候选栏计算公式，故不虚构常数。

## 七、端到端切换时序

```text
用户点“下一键盘”键
  │
  ├─ GlobalKeyManager onNextKeyboard
  │    └─ dataSource onGlobalSelectNextKeyboard:1
  │         └─ iFlyKeyboardController
  │              └─ iFlyKeyboardContainer changeCurrentKeyboardToNext
  │                   ├─ 枚举启用的 InputModeItem
  │                   ├─ 跳过禁用项
  │                   └─ 到尾环回 / fallback
  │
  └─ 或用户在选择面板点指定项
       └─ GlobalKeyManager onSwitchToKeyboard:type
            ├─ state==5：特殊服务 + 通知/埋点
            ├─ else：普通 dataSource 切换
            └─ delegate onGlobalSwitchToKeyboard:type
                 │
                 ├─ KeyboardTypeManager getNewKBType(...)（场景修正）
                 ├─ KeyboardLayoutManager / UI controller 取 KBStruct
                 ├─ IniFileParser(path, completion)
                 │    └─ INI → dictionary → KeyStructGenerator
                 ├─ KBHeightAdjustMgr：baseHeight + configuredDelta
                 ├─ BaseLayoutAdjustManager：缩放/贴边/单手镜像
                 ├─ iFlyInputManager reloadKeyboard(... keyboardType ...)
                 ├─ XFKeyBoard / 子键视图重建
                 └─ GlobalKeyManager.inputView 指向当前视图（weak）
```

`onKeyboardRebuild` 是“不改变目标类型，仅重建当前资源”的旁路，皮肤、尺寸、旋转、返回键状态变化可直接触发该路。

## 八、键盘类型枚举表（证据分级）

### 8.1 已确认数值

| 内部值 | 在决策器中的来源 | 产品名称 |
|---:|---|---|
| 11 | 默认；场景8；插件覆盖 userFlag=true | 待验证 |
| 12 | 场景0/2/6族且 security=true | **安全输入专用类型**（功能已确认，具体布局名待验证） |
| 13 | 场景1、5 | 待验证 |
| 14 | 场景4 | 待验证 |

## 九、建议的可移植架构

```c
typedef struct {
    KBType normalPrimary;
    KBType normalFallback;
    double normalHeightDelta;
    double oneHandHeightDelta, oneHandWidthDelta;
    int oneHandMode;
} PortableKBConfig;

typedef struct {
    KBType type;
    const char *iniPath;
    KBStruct *layout;
    View *view;
} KeyboardSession;

void SwitchKeyboard(KeyboardRuntime *rt, KBType requested) {
    KBType chosen = NormalizeType(requested, rt->security,
                                  rt->plugin, rt->user, &rt->config);
    const char *path = ResolveLayoutPath(chosen, rt->orientation,
                                         rt->skin, rt->config.oneHandMode);
    ParseIniAsync(path, ^(Dictionary *dic) {
        if (!dic) { ShowFallbackKeyboard(rt); return; }
        KBStruct *s = BuildKBStruct(dic);
        CGRect area = ComputeKeyboardArea(rt->device,
                                          rt->candidateBarHeight,
                                          rt->safeAreaBottom);
        area.size.height += EffectiveHeightDelta(&rt->config);
        AdjustKBStruct(s, area, rt->config.oneHandMode);
        View *v = BuildKeyboardView(s, chosen);
        rt->session = (KeyboardSession){chosen,path,s,v};
        PresentInputView(rt, v);
    });
}
```

移植约束：解析必须允许异步；切换请求需带 generation token，防止旧 completion 覆盖新键盘；inputView 可弱持有，但 controller 必须强持有；安全键盘类型必须在普通偏好之前覆盖。

## 十、事实、推断与待验证项

### 已确认事实

- 类型决策参数寄存器、0…8 跳表、返回值集合和 security 覆盖条件。
- plugin 四级短路谓词以及 `userFlag ? 11 : dynamicB` 覆盖。
- GlobalKeyManager 使用 weak dataSource/delegate/inputView 并仅负责协议转发。
- FileParser 基类同步 `completion(nil)`；IniFileParser 捕获并转发 completion。
- 两个 `set*View:` 是属性桥接，不是高度算法。
- 高度变更存在明确 `base + delta`；布局调整存在 mode==2 镜像。

### 推断（均有依据）

- dynamicA/B 是 KeyboardConfig 中两个键盘类型配置 getter：依据两者返回值被直接作为 KBType，且参数对象明确为 keyboardConfig。
- 候选栏/安全区在 inputHeightManager 或 DeviceBaseHeight 中合成：依据 reload API 显式接收 inputHeightManager，而 setter 无相应 selector。
- `resolveInstanceMethod:` 服务于通用配置属性：依据固定 resolver + 大量成对 getter/setter。

### 待验证项与下一步

1. 解码 `0x1017c2d38`、`0x1017aa920` 等 selref，恢复 plugin 四谓词、dynamicA/B、userFlag 的准确 selector。
2. 在 LLDB/Frida hook `getNewKBType...` 与 `KeyboardLayoutManager getDisplayNameWithKeyboardType:`，遍历 0…20，建立编号→拼音/笔画/英文/手写/符号/数字的权威表。
3. hook `IniFileParser` completion 的线程与返回类，确认异步队列和失败对象语义。
4. 扩展反汇编 inputHeightManager 的设备基准高度、候选栏高度和 safe-area getter，补齐具体公式与常数。
5. 对 `iFlyKeyboardContainer changeCurrentKeyboardToNext` 解码所有 selector，恢复启用列表来源、过滤谓词和 fallback type 名称。
